# 機能追加ワークフロー

## 推奨モデル
| 機能の規模 | 推奨モデル |
|---|---|
| 小 (1-2ファイル変更) | Gemini 3.1 Pro (Low) |
| 中 (3-5ファイル, 新規コンポーネント) | Gemini 3.1 Pro (High) |
| 大 (新ページ, データモデル変更) | Gemini 3.1 Pro (High) |

## 前提条件
- `.agents/context/CODEBASE_MAP.md` を読み、関連ファイルと構造を把握する
- `.agents/context/ARCHITECTURE.md` を読み、設計パターンを理解する
- `.agents/context/POKER_RULES.md` を読む（ポーカー機能の場合）
- `PROJECT_CONSTITUTION.md` 全体を確認する

## ワークフロー

### Step 1: 要件の構造化
ユーザーから受け取った情報を以下の形式に整理する。不足情報があれば **1問ずつ** 質問する。

```
- 機能名:
- 対象画面:
- ユーザーストーリー: 〜として、〜したい。なぜなら〜。
- 受け入れ条件:
  - [ ] ...
  - [ ] ...
```

### Step 2: 影響範囲分析
`.agents/context/CODEBASE_MAP.md` を参照し、以下を特定する:
- **変更が必要なファイル** のリスト
- **新規作成が必要なファイル** のリスト
- **影響を受ける既存機能**（回帰リスク）

影響範囲をユーザーに報告し、承認を得る。

### Step 3: 実装計画の作成
`implementation_plan.md` を作成し、以下を含める:
- 変更するファイルと変更内容のサマリー
- 新規ファイルの設計
- 型定義（Zodスキーマ）の設計
- UIのモックアップ（必要に応じて）

ユーザーの承認を待つ。

### Step 4: TDDプラン作成 (Plan)
`PROJECT_CONSTITUTION.md` §8 に従い、TDDプランを作成する:
- テストすべき項目のチェックリスト
- 入力、出力、例外を網羅する
- 複雑なロジックは小さな単位に分解する

### Step 5: TDDサイクル実行
以下を繰り返す:

#### 5a. テスト作成 (Red)
TDDプランの次の項目のテストを作成する
// turbo
`npm test` で失敗を確認する

#### 5b. ミニマム実装 (Green)
テストをパスさせる最小限の実装を行う
// turbo
`npm test` で成功を確認する

#### 5c. リファクタリング (Refactor)
コードを整理・最適化する
// turbo
`npm test` で全テスト通過を確認する

### Step 6: 統合テスト
// turbo
1. `npm run build` が成功することを確認する
// turbo
2. `npm test` で全テストスイートが通過することを確認する
3. 新規機能が既存機能に影響していないことを確認する

### Step 7: ドキュメント同期（必須）
以下のファイルを確認し、すべて更新する:
1. `.agents/context/CODEBASE_MAP.md` — 新規ファイルの追加、ファイルグルーピングの更新
2. `.agents/context/ARCHITECTURE.md` — 新しいルート、コンポーネント、型などの追記
3. `.agents/context/POKER_RULES.md` — ポーカーロジックの変更がある場合は更新
4. `README.md` — ユーザー向け機能の説明を追加

### Step 8: 知識抽出の提案 (任意)
今回の機能実装を通じて「プロジェクト特有の強力な教訓パターン」や「再利用できる手順」を発見した場合、ユーザーに以下のように提案する:
`「今回の実装手順は、再利用可能なルール（またはスキル）として /extract-knowledge で抽出・保存しておくことをお勧めしますが、いかがでしょうか？」`

### Step 9: 完了報告
以下の形式で報告する:
```
## 機能追加完了
- 機能名: ...
- 追加ファイル: ...
- 変更ファイル: ...
- テスト: ✅ 全パス (追加テスト数: N件)
- ドキュメント更新: ✅ CODEBASE_MAP.md, ARCHITECTURE.md 等
```
