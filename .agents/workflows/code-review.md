# コードレビューワークフロー

## 推奨モデル
| レビュー対象 | 推奨モデル |
|---|---|
| 小規模変更 | Gemini 3.1 Pro (Low) |
| 大規模/重要変更 | Claude Sonnet 4.6 (Thinking) |

## 前提条件
- `PROJECT_CONSTITUTION.md` を確認する
- `.agents/context/ARCHITECTURE.md` を読み、設計パターンを理解する
- `.agents/quality/CHECKLIST.md` を読み、チェック項目を把握する

## ワークフロー

### Step 1: 変更差分の把握
// turbo
`git diff` または指定された変更内容を確認し、変更の概要を整理する:
- 変更ファイル一覧
- 変更の目的（バグ修正 / 機能追加 / リファクタリング）

### Step 2: PROJECT_CONSTITUTION 準拠チェック
以下の規約に違反していないか確認する:

- [ ] **§2 技術スタック**: 許可されていないライブラリの追加がないか
- [ ] **§5 コーディング規約**: 命名規則（PascalCase / camelCase / UPPER_SNAKE_CASE）
- [ ] **§5 TypeScript**: `any` 型の使用がないか
- [ ] **§5 コンポーネント**: Functional Component + Hooks のみか
- [ ] **§1 FP原則**: 副作用が最小限か、純粋関数が推奨されているか

### Step 3: アーキテクチャ整合性チェック
`.agents/context/ARCHITECTURE.md` に従い:

- [ ] 各レイヤーの責務を越えていないか（UIロジックにDB操作が混在していないか等）
- [ ] 既存のデータフローパターンに従っているか
- [ ] 新しい型はZodスキーマで定義されているか

### Step 4: テスト品質チェック
// turbo
- [ ] `npm test` が全パスするか
- [ ] 新規ロジックにユニットテストが追加されているか
- [ ] エッジケースがカバーされているか

### Step 5: モバイル / オフライン対応チェック
- [ ] タップ領域が 48px 以上か
- [ ] レスポンシブデザインが適用されているか
- [ ] サーバー通信を行っていないか（オフラインファースト）

### Step 6: 品質チェックリスト最終確認
`.agents/quality/CHECKLIST.md` の全項目を確認する。

### Step 7: 知識抽出の提案 (任意)
コードレビューを通じて「チームで頻繁に起きる間違い」や「新しく定着させるべき設計パターン」を発見した場合、ユーザーに以下のように提案する:
`「今回のレビューで指摘した事項は、再利用可能なルールとして /extract-knowledge で抽出・保存しておくことをお勧めしますが、いかがでしょうか？」`

### Step 8: レビュー結果の報告
```
## コードレビュー結果
- ステータス: ✅ 承認 / ⚠️ 要修正 / ❌ リジェクト
- 問題点: (あれば列挙)
- 改善提案: (あれば列挙)
- 良い点: (あれば列挙)
```
