# リファクタリングワークフロー

## 推奨モデル
| リファクタの規模 | 推奨モデル |
|---|---|
| 単一ファイル | Gemini 3.1 Pro (Low) |
| 複数ファイル横断 | Gemini 3.1 Pro (High) |

## 前提条件
- `.agents/context/CODEBASE_MAP.md` を読み、対象ファイルの依存関係を把握する
- `.agents/context/ARCHITECTURE.md` を読み、リファクタリング後のあるべき姿を理解する
- `PROJECT_CONSTITUTION.md` §8.1（TDDサイクル）の Refactor ステップに準拠する

## ワークフロー

### Step 1: リファクタリングの目的確認
ユーザーからの指示を以下に整理する:

```
- 対象: （ファイル名 or モジュール名）
- 目的: （可読性向上 / パフォーマンス改善 / 重複排除 / 責務分離 等）
- 制約: （外部インターフェースの変更可否）
```

### Step 2: 現状分析
// turbo
1. 対象ファイルを読み、現在の構造・問題点を分析する
2. 依存関係を特定する（何がこのファイルをimportしているか）
// turbo
3. 既存テストの有無と内容を確認する

### Step 3: リファクタリング計画
以下を策定してユーザーに提示する:
- 変更前後の構造比較
- 影響を受けるファイル
- リスク評価

### Step 4: 既存テストでの基準設定
// turbo
1. `npm test` を実行し、現在のテスト結果を記録する
2. テストがない場合は、リファクタリング前に回帰テストを追加する

### Step 5: 自動検証と自律修復ループ (Autonomous Verification Loop)
1. 小さな単位でリファクタリングの変更を行う。
// turbo
2. `npm run build` および `npm test` を実行する。
3. **自律修復**: もしエラーやテスト失敗が発生した場合、ユーザーに報告する前に **AI自身が自律的に** エラーログを分析し、コードを再修正（または元に戻す）して再度テストを実行する。
4. この自己修復ループをテストがパスするか、最大3回の試行上限に達するまで繰り返す。上限に達した場合は状況をユーザーに報告して介入を求める。
5. リファクタリングの目的が達成されるまで、この段階的な変更と自律修復（1〜4）を繰り返す。

### Step 6: ドキュメント同期（必須）
以下のファイルを確認し、コード変更に伴う更新が必要かチェックする:
1. `.agents/context/CODEBASE_MAP.md` — ファイル分割/統合があった場合は更新
2. `.agents/context/ARCHITECTURE.md` — アーキテクチャパターンの変更があった場合は更新

### Step 7: 知識抽出の提案 (任意)
今回のリファクタリングを通じて「よりクリーンな設計パターン」や「アンチパターンの回避方法」が得られたと感じた場合、ユーザーに以下のように提案する:
`「今回のリファクタリング方針は、再利用可能なルールやスキルとして /extract-knowledge で抽出・保存しておくことをお勧めしますが、いかがでしょうか？」`

### Step 8: 完了報告
```
## リファクタリング完了
- 対象: ...
- 変更内容: ...
- 改善効果: ...
- テスト: ✅ 全パス
- ドキュメント更新: ✅ / 不要
```
