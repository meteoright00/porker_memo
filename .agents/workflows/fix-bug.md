# バグ修正ワークフロー

## 推奨モデル
| バグの深刻度 | 推奨モデル |
|---|---|
| 軽微 (UI崩れ, typo) | Gemini 3 Flash |
| 中程度 (機能不具合) | Gemini 3.1 Pro (Low) |
| 重大 (データ不整合, ロジックバグ) | Gemini 3.1 Pro (High) |
| 致命的 (原因不明, 再現困難) | Claude Sonnet 4.6 (Thinking) |

## 前提条件
- `.agents/context/CODEBASE_MAP.md` を読み、関連ファイルを特定する
- `.agents/context/POKER_RULES.md` を読み、ドメイン知識を把握する（ポーカーロジック関連の場合）
- `PROJECT_CONSTITUTION.md` §9（デバッグと自己修正）に従う

## ワークフロー

### Step 1: バグの構造化
ユーザーから受け取った情報を以下の形式に整理する。不足情報があればユーザーに **1問だけ** 質問する。

```
- 画面: （例: トーナメント詳細ページ）
- 再現手順: （例: チップ記録ボタンをタップ → 金額入力 → 送信）
- 期待する動作: （例: チップが記録される）
- 実際の動作: （例: エラーが発生する / 何も起きない）
```

### Step 2: 関連コードの特定
// turbo
`.agents/context/CODEBASE_MAP.md` の「機能別ファイルグルーピング」と「ホットスポット」を参照し、バグに関連するファイルを特定する。

### Step 3: 根本原因分析 (Root Cause Analysis)
`PROJECT_CONSTITUTION.md` §9.1 に従い、以下を分析する:
- **どこで** 起きているか（スタックトレース、該当コード行）
- **なぜ** 起きたか（論理的欠陥、想定外の入力、型不整合など）
- 根本原因を言語化して報告する

### Step 4: 自己反省 (Self-Reflection)
`PROJECT_CONSTITUTION.md` §9.2 に従い、修正前に以下を記述する:
- なぜその間違いが起きたのか（思考の盲点）
- 同じ過ちを繰り返さないための教訓

### Step 5: テスト作成 (Red)
`PROJECT_CONSTITUTION.md` §8 (TDD) に従う:
1. バグを再現する失敗テストを作成する
// turbo
2. `npm test` で失敗することを確認する

### Step 6: 修正実装 (Green)
1. テストをパスさせる **最小限の** 修正を行う
// turbo
2. `npm test` で成功することを確認する

### Step 7: リファクタリング (Refactor)
1. テストが通る状態を維持しながら、コードを整理する
// turbo
2. `npm test` で全テスト通過を確認する

### Step 8: 回帰テスト
// turbo
1. `npm run build` が成功することを確認する
// turbo
2. `npm test` で全テストスイートが通過することを確認する

### Step 9: ドキュメント同期（必須）
以下のファイルを確認し、コード変更に伴う更新が必要かチェックする:
1. `.agents/context/CODEBASE_MAP.md` — ファイル追加/削除/移動があった場合は更新
2. `.agents/context/ARCHITECTURE.md` — アーキテクチャ変更があった場合は更新
3. `.agents/context/POKER_RULES.md` — ドメインロジック変更があった場合は更新
4. `README.md` — ユーザー向け機能変更があった場合は更新

### Step 10: 完了報告
以下の形式で報告する:
```
## バグ修正完了
- 根本原因: ...
- 修正内容: ...
- 変更ファイル: ...
- テスト: ✅ 全パス
- ドキュメント更新: ✅ / 不要
```
